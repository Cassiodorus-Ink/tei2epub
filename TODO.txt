# tei2epub TODO

## Internal representation: <front> and editorial matter

Consider adding an explicit internal-representation node for <front>
content (and perhaps more generally for extended editorial comments).
Currently <front> is normalised into a plain Chapter on the Work's
``preamble`` field.  That is adequate for rendering, but it loses the
semantic distinction between primary text and editorial preface.
A dedicated ``FrontMatter`` or ``EditorialNote`` node would let the
renderer choose different styling, and would make round-trip or
structural analysis easier.

## Internal representation: inline emphasis

a. Should the internal model object be named `Emph` rather than `Hi`?
   `Hi` mirrors the TEI element name, but the object represents
   emphasis/italic in the output and the TEI source for that is `<hi>`,
   `<emph>`, `<i>`, or `<b>` — "Hi" is a confusing name for someone
   reading the model.  `Emph` (or `Italic`) would be clearer.

b. Should `<b>` (HTML bold leak) produce a distinct `Bold` model node
   rather than being silently collapsed into `Hi`/`Emph`?
   Currently all four tags (`<hi>`, `<emph>`, `<b>`, `<i>`) map to the
   same node and render as `<em>` (italic).  This means source-side bold
   becomes italic in the EPUB, which is a semantic mismatch.  Options:
   - Keep as-is (pragmatic: bold doesn't appear intentionally in these
     texts, it's always a conversion artefact or scan noise).
   - Add a `Bold` node rendered as `<strong>`, and route `<b>` there.
   - Inspect `<hi rend="bold">` and route accordingly, treating bare
     `<b>` as a scan artefact to drop or italicise.

## Verse lines (<l>) inside <p>: implicit VerseBlock splitting

506 corpus files use bare `<l>` directly inside `<p>` for quoted verse,
which is technically invalid in both TEI P4 and P5 (where `<l>` is
block-level and should sit inside `<lg>`, not `<p>`).  Only 5 files use
`<lg>` at all.  Currently these lines render as inline `<span>` elements
with `<br/>`, losing block-level formatting; `rend="indent"` on a verse
line inside `<p>` is also silently ignored because the CSS rule for
`verse-indent` only covers the `blockquote.verse` context.

Proposed fix: extend `_parse_p_to_blocks` to detect runs of `<l>`
children and emit them as a `VerseBlock`, mirroring the existing
`<list>`-inside-`<p>` split logic.  Edge cases to handle:

  - Non-whitespace tail after `</l>` → ends the verse group, resumes
    prose as a new Paragraph.
  - `<pb>` between `<l>` siblings → transparent (page boundary only);
    do not interrupt the verse group.
  - `<note>` between `<l>` siblings → absorb as inline on the preceding
    line, or skip; do not interrupt.
  - Also add `"l"` to `P_CHILDREN` in coverage.py once implemented.

Effort: ~30–40 lines in parse.py, plus coverage.py update.

## TL-7: <note> with block-level structural children (2026-05-03)

New check added to the corpus checker.  Out of 296,162 <note> elements,
114 files contain <note> with structural children (<div1>, <div2>,
<div3>, <head>, <list>, <lg>).

109 of those are the Admonitio pattern (<note> as direct child of
<body> wrapping the whole work) and ARE handled by parse().

6 files are flagged by TL-7 as genuinely problematic (structure will
be flattened to plain text):

  - willelmus-malmesburiensis/179_Willelmus-Malmesburiensis_De-gestis-
    pontificum-Anglorum.xml
    <div2> inside <note>

Additionally, auctor-incertus-tertullianus/002_Auctor-incertus-
(Tertullianus_)_Adversus-Marcionem.xml has 5 <note> elements containing
<head> inside inline contexts (inside <head> or <l> elements).  These
are editorial footnotes with bold headings; the text survives but the
heading semantics are lost.

Remediation: editorial prefaces inside <note> should be converted to
<front> (if at the work level) or to ordinary <div1>/<div2> structure
(if inline within the text).  Run::

    poetry run python scripts/check_corpus.py --text-loss --report tl7.txt

to regenerate the full TL-7 report.
